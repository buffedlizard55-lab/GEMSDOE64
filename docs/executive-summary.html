Step 3 — what the format must be, and why the earlier upload was rejected

The published format (competition page 967) requires: the same projected CRS as the training data (EPSG:32611); the same resolution (100 m); the same bounds, with data outside the bounds null or NaN; a single float32 layer with values between 0 and 1 indicating probability of fault presence.

The earlier rejection "Predicted values must be in range [0, 1]" has two distinct mechanisms, both measured in this repository against the real rasters:

MechanismRoot causeFix
A — NaN inside the footprint The footprint mask was derived from a single feature band. Band 1 has 5,165,852 valid in-footprint cells against the template's 5,167,373, so 3,061 scored pixels were stranded as NaN. The form's test ((v>=0)&(v<=1)).all() is False for NaN. Take the footprint from sample_submission.tif (the official template), never from a feature band.
B — a finite value outside [0, 1] The feature sentinel -3.4028234663852886e+38 survived into the output on those same 3,061 in-footprint cells. Replace the sentinel with NaN before any arithmetic, then write an all-finite raster: zeros outside the footprint, values in [0,1] inside, and no nodata tag.

The organizer's own reference notebook writer passes no nodata= argument and writes finite sigmoid output, so all-finite-and-untagged is what the reference solution itself produces. The ledger in the sibling repositories shows the all-finite and NaN-outside twins of the same artifact scoring identically, so the fix costs nothing.

scripts/validate_submission.py enforces all of this and is the gate that ran above. Run it yourself on any file before uploading:

python scripts/validate_submission.py docs/downloads/*.tif
