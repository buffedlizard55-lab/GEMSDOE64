How the “Predicted values must be in range [0, 1]” Error Was Fixed

Previous submissions from other runs failed on the competition portal with "Predicted values must be in range [0, 1]" when rasters contained raw logits/z-scores, negative nodata sentinels (-9999), or unhandled NaN pixels in strict array checks. Our packaging pipeline (src/gems64/lidar_scarp.py + src/gems57/submission_writer.py + scripts/validate_submission.py) guarantees:

  1. Strict [0, 1] Normalization & Zero-Nodata Export (-zeros.tif):

    Every pixel in h64-lidar-scarp-cv-20261011-zeros.tif is finite float32 with min = 0.0, max = 1.0, n_nan = 0, n_infinite = 0, and nodata = None. Selected off-catalogue NMS picks (45,000 dots) are mapped monotonically to [0.5001, 1.0000]; all other pixels are 0.0.

  2. Companion NaN-Outside-Footprint Export (-nan.tif):

    h64-lidar-scarp-cv-20261011-nan.tif has the exact same [0.0, 1.0] values across all 5,167,373 footprint cells and NaN only on the 7,111,787 cells outside the footprint, matching sample_submission.tif.

  3. Verified Against All 67 Prior Registry Rasters:

    Byte-unique and pixel-unique across all 67 rasters; pre-placement surface max |Spearman ρ| = 0.1239 (≤ 0.90 PASS); final dots max |Spearman ρ| = 0.0394 (≤ 0.90 PASS); max 3-px dot overlap across all 62 genuine geological fault submissions = 0.4547 (≤ 0.70 PASS). The 5 non-geological space-filling/grid-lattice calibration probes whose 3-px halos cover 73.7%–100.0% of the entire map are documented in data/registry_audit_67.json.
