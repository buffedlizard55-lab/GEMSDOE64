First check: is the file approved?

Not yet. The overview must show a green, downloadable candidate and a passing run card before you select any file for submission. Right now it shows a red stop state. Do not substitute an old sibling-site TIFF or a synthetic/all-zero raster.

When a validated candidate exists: upload it manually

  1. Sign into the official DrivenData competition account and review the current rules. The competition data tab redirects to login. This project will not store credentials, log in automatically, or bypass the access gate.
  2. Check the candidate receipt before upload. Confirm the file's SHA-256, unique filename, note, and validator output against the green status shown on this site. No such candidate is currently available.
  3. Open DrivenData's New submission form. In “File to submit,” choose the approved single-band .tif, or a .zip containing exactly one GeoTIFF if required by the portal.
  4. Enter the unique run name and short note. Use the exact name and note shown beside the approved download. The note should identify the method and evidence status; never call a projection an organizer score.
  5. Submit and retain the platform receipt. Record the submission identifier, the file hash, the displayed result, and the receipt date. Only a receipt supports an ORGANIZER-CONFIRMED result in this project's run card.

Required GeoTIFF format

The official problem description requires all of the following:

  • One raster band, datatype float32.
  • Prediction/confidence values in the closed interval [0, 1].
  • Projected CRS EPSG:32611 (UTM zone 11N), matching the training/template data.
  • 100 m resolution and the exact training/sample-submission bounds, shape, and geotransform.
  • Null/NaN outside the required bounds/footprint. The valid footprint must contain no NaN, nodata sentinel, or value outside range.

Do not guess the raster dimensions or transform. Copy them from the official sample/template and compare every field. The sample GeoTIFF and training files are not in this checkout, so no dimensions or transform are claimed here.

If the portal says “Predicted values must be in range [0, 1]”

The reported error is a format/range failure, not evidence that a method scored poorly. Re-open the exact written TIFF and check the minimum and maximum across every in-footprint pixel, then inspect nodata metadata and sentinel values. Confirm finite in-footprint values are within range and that null/NaN values occur only outside the footprint. Re-check that the writer used the official sample grid.

This checkout has no rejected TIFF to inspect, so its cause is not diagnosed here. No claim is made that the rejection was specifically caused by NaN or any particular nodata sentinel.
