Troubleshooting the rejection

“Predicted values must be in range [0, 1]”

The message means the submission checker found one or more values it did not accept as valid probabilities. It does not, on its own, identify which pixel or prove that the model's unmasked predictions are wrong: the cause can be the values, the nodata/mask semantics, or the way the raster was serialized. Inspect the exact rejected file and official validator output; do not guess.

Check finite minimum and maximum on the scored footprint

Compute counts of NaN, positive infinity, negative infinity, values below 0 and values above 1. Report the offending count and coordinates. First confirm that your validity mask matches the submission sample.

Confirm the model output is a probability, not a score/logit

Common bugs include exporting raw logits or signed decision values, a z-scored layer, an unbounded regression surface, or an 8-bit 0–255 band. Apply the documented sigmoid/calibration/normalization in the intended pipeline and write floating point—not an arbitrary byte conversion.

Check nodata and outside-mask behavior

A sentinel such as −9999, NaN or a masked value may be acceptable only outside the template's valid footprint and only if the validator recognizes it as nodata. If a sentinel is written into scored pixels—or the writer omits the nodata mask—the range checker may reject it. Conversely, replacing outside-footprint nodata with zero can change validity semantics. Follow the shared writer and sample exactly.

Inspect GeoTIFF band, dtype and scale/offset metadata

Verify one band and the required float dtype; check scale/offset tags, mask band, nodata tag, compression and pixel type. A reader may expose stored values differently if scale/offset metadata or integer quantization is wrong.

Re-run the official/shared validator on the exact candidate bytes

Do not “fix” the error by blindly clipping values to [0,1]. Clipping can hide a broken export, flatten the ranking, alter the score, or turn sentinels into plausible predictions. Correct the upstream cause, regenerate through the shared writer, validate, hash, and only then consider upload.

Good diagnostic record: input SHA-256; band count, dtype, CRS, transform, shape and bounds; nodata value and valid-mask definition; counts/min/max of finite valid pixels; counts of invalid values inside and outside the footprint; first few offending row/column coordinates; exact validator version/message. Keep the rejected file and its receipt private/secure where appropriate; do not overwrite it before diagnosis.

Future upload hand-off

A controlled sequence for a genuinely cleared raster

These are general operator steps. Always follow the active competition's official upload page and current rules; do not upload anything from this branch unless its release gate is green.

Confirm enrollment and current competition instructions

Sign in using the entrant's own authorized account; open the official competition submission page and check eligibility, phase-specific rules, accepted file type and any current naming instructions.

Review the completed machine-readable run card

Confirm all method, holdout, confidence-interval, mimic, leakage, novelty and exact-byte evidence is present. A projected score or sibling-page claim cannot satisfy this step.

Lock and verify the deliverable

Run the shared writer and validator on the final raster. Record SHA-256, unique never-reused submission name and a note of no more than 140 characters (a GEMSDOE64 project requirement). Confirm the staged upload bytes match the recorded hash.

Upload manually through the official form

Choose the correct challenge/phase and upload only the required deliverable in the form's accepted format. If the form's instructions conflict with this guide, stop and resolve the conflict from official rules/sample tooling; do not invent a wrapper format.

Save the organizer receipt and reconcile attribution

Save the submission identifier, timestamp, name/comment, uploaded-file hash if shown, and official score/receipt. Label an evaluator score `ORGANIZER-CONFIRMED` only when the receipt links that exact artifact. Never infer the score for an unlinked local file.
